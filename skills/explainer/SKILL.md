# Explainer

An explainer is a page that explains a system, a plan or a comparison with visuals first. Readers read explainers instead of long text.

## When to load it

Load this skill first, before the generic artifact or design guidance, when someone asks for:

- a visual, an artifact, a page, a report, a dashboard, a diagram, a chart, a widget or a before/after;
- an explanation, more detail, how something works, a comparison, a map or a plan.

This skill holds the page contract (tokens on `:root`, the dark blocks, the body background, phone width), so the generic guidance adds nothing to an explainer page. When the harness needs a call first (for example the Artifact tool's `quickstart`), make that call, then build the page from this kit.

The user's own words win over this skill. A theme the user names wins over "Pick the theme" below.

## Pick the format

An explainer page is one reply format. Read `references/formats/README.md` and use the first row that fits the reader's need. A finished user interface change gets a user interface walkthrough video (`references/formats/ui-walkthrough.md`): record the working path, check each step frame, then cite it. Audio replies, generated video and generated images are planned rows with no guide yet.

## Make a page

1. Read `references/pattern.md` and `references/creative.md`. Name the subject's own shape (three candidates, pick one) and draw the hero as that shape with `kit/draw.js`, never as a kit box diagram. Then pick one visual per section by the question it answers (pattern.md, "Choose the diagram"), from `references/charts.md`: great or good only. After the hero, the default is a connection diagram with icons or logos on its parts. Dates take a timeline, causes a tree, items of the same kind take tabs. A table is the last resort: at most one shows at load, never first in a section. For each main concept, pick the best primary view, then add at least one alternative view of the same subject from a different family (structure, time, amount, hierarchy, or comparison). The view switch, tabs or a second figure can carry it. A table can be an alternative view only, never the primary one.
2. Copy `examples/starter.html` next to the other examples (or copy `kit/` next to your page and fix the seven paths).
3. Pick the theme (below) and set it in `<meta name="ex-theme" content="<id>">`.
4. Write one `.ex-section` per subject. Each opens with an ExplainerHead whose first sentence defines the subject.
5. Put every part in `window.EX` as `{"t": title, "l": layer, "d": definition, "x": [facts]}`. The definition says what the part is. Facts never repeat it. Give each main item about 4 to 8 substantive facts: why it exists, how it works, how it connects to its neighbours, real numbers, limits and failure modes, and a source or a link where one exists.
6. Draw the hand-drawn figures with `ExDraw` and each rated chart with `ExCharts.<kind>(element, data)`. Draw at least half of the sections by hand. Load `kit/themes.js`, `kit/charts.js`, `kit/draw.js` and `kit/canvas.js`, and draw every figure, before `kit/explainer.js`. A figure that should not open on the canvas gets `data-canvas="off"`; a figure outside an `.ex-figure` gets `data-canvas` to opt in. When a subject needs two families, use a second figure or `ExCharts.views`. For one set of rows, `ExCharts.data(element, {label, unit, rows})` switches among a bar chart, a table, and a share diagram.
7. End a section with `<details class="ex-facts" data-def="…">` when a reader will want to scan the facts.
8. Answer the creative check in `references/creative.md`. Fix each miss now, not in a later round. Then run `scripts/check <page.html>`. Fix every failure. Set `CHROMIUM_PATH` to use a browser that is already installed.
9. Look at the screenshots (`--shots <dir>`). Read the page as a reader would: the hero is a picture of the subject, named products show their logos, things show icons, one flow moves, at least four patterns, no open text longer than one sentence, every fact has a part, red on one or two things only, and no section that reads as a spreadsheet. Each main concept has two views from different families. Each main pop-up has about 4 to 8 facts. Full words only. The problem is a drawn figure. Unknowns are question marks or dashed lines. A story strip is stamped HYPOTHETICAL. A proposed after view is stamped PROPOSAL, NOT APPROVED.

## Picture rules

- Draw the subject, not boxes about it. The hero is the subject's real-world shape (`references/creative.md`).
- A named product, company or model maker shows its real logo, on a figure, a chart mark, a legend or a pick list.
- A kind of thing (a person, an agent, a server, a key) shows an icon.
- A comparison of many options is a live chart: logos as marks, a shaded good quadrant, limit lines, a best-value line, a ringed winner, and filters that redraw it.
- A hard mechanism gets an analogy figure stamped ANALOGY, with the real mechanism as the second view. A transform gets a worked example on one synthetic value.
- Show the problem as a picture. Drawn figures carry it. The open page has almost no paragraphs.
- Where the subject is a threat or a failure, show it in motion. Animate the paths and the dots. Set them against real live numbers.
- Draw risk as a blast radius. Rings spread outward from the point of impact. A solid ring is confirmed. A dashed ring is not checked.
- A story strip is allowed when it is clearly stamped HYPOTHETICAL. Each step shows which fix would have stopped it.
- Add a good-example contrast figure beside a bad case.
- When the page proposes a change, redraw the main picture as an after view. Stamp that figure PROPOSAL, NOT APPROVED. Keep the alternative view from the other family as well.
- Keep the visuals honest. Show an unknown as a question mark or a dashed line. Leave a guess off the figure.

## Colour, fonts and radii: tokens only

- Every colour, font, radius and chart series reads a variable from `kit/tokens.css`. Never write a hex, `rgb()`, `oklch()` or a colour name in a page or in chart code. `scripts/check` fails on one.
- Data series use `--series-1` to `--series-5`. Diagram boxes that carry a meaning use the diagram colour key (`--key-*`). Never mix the two.
- Never add a theme switcher to a component. The page has one theme button; the runtime adds it.
- Never add a zoom or full-screen control to a figure. `kit/canvas.js` gives every figure the same open button: a pop-up for data charts, the canvas for diagrams. The button is an icon with a hover name; never add a text label to it.
- A style rule on `.ex-figure svg` also reaches the icon inside each figure's open button, because the button sits in the figure. Scope a figure rule to the drawing, or reset it for `.ex-figure .ex-expand svg` (as `kit/canvas.js` does). Before 27 October 2026, `.ex-figure svg { min-width: 760px }` drew the Expand icon 760px wide over the page. `scripts/check` fails when a button icon is larger than 24px.
- Kit code never adds a `<style>` tag at run time. The claude.ai Artifact viewer blocks it, and the figure button then draws its icon across the whole figure. Kit scripts add their styles with `document.adoptedStyleSheets`. `scripts/check` loads the page under the viewer's kind of style policy and fails when a figure button is not a 28px icon with a hover name. A local screenshot without that policy is not proof.

## Pick the theme

The page names one theme; the viewer can change it. Use the first rule that fits:

1. The user names a theme: use it.
2. The page is about a repo or product with its own `DESIGN.md` or theme: use that theme if the registry has it.
3. The page is about Flow, or a Flow screen, job, invoice or report: `harbour`. A page for a Flow installation that uses Meridian: `meridian`.
4. Long reading, learning material, public docs or a shadcn/ui product: `clarity`.
5. Anything else: `clarity`, the default reading theme. It embeds licensed regular and bold OpenDyslexic, not a Google Fonts URL or a local-font assumption. It is a preference, not a medical treatment or a claim of universal reading benefit. Arc Forge remains an unchanged separate choice and emergency fallback.

The viewer's choice wins: the theme menu keeps "Set as default" for the viewer, and the order is the viewer's pick for this view, then the viewer's saved default, then the page theme, then Arc Forge. An artifact keeps the saved default in localStorage. Publish with `capabilities: {db: {}, user: {}}` only when the default must follow the viewer to other devices.

To add a theme, add it to its owner (`arcforgelabs/themes` for a shadcn preset, Flow for a Flow family) and run `scripts/sync-themes <themes> <flow>`. Never edit `kit/themes.js` by hand.

## Deliver the page

OpenClaw is the public support target. Read `references/openclaw-delivery.md` before delivery: a substantial explainer gets a full responsive artifact AND a compact inline companion from the same facts. Native controls and saved records first; never fabricate a decision or status control. Claude Code and Cursor below are basic internal fallbacks, not public parity.

The source page is the same everywhere. Only the delivery changes.

| Harness | Delivery |
| --- | --- |
| OpenClaw | Bundle the full page, deliver it through the advertised artifact/HTML surface, then add the native inline companion described in `references/openclaw-delivery.md`. |
| Claude (claude.ai, Claude Code with the Artifact tool) | `scripts/bundle page.html out.html`, then publish `out.html` with the Artifact tool. Reply with one line and the link. |
| Cursor (Agent Window) | Follow `artifact-preview` for any HTML page, explainer, or image. Serve on the machine that runs the reader's browser, or cite a link that machine can reach. Check the port with `lsof` on that machine first. Never cite `127.0.0.1`, `localhost`, or `0.0.0.0` from a cloud VM or from a different computer. Do not cite a store path. |
| Any agent on a workstation (Codex, Grok, Claude Code) | Serve the skill folder: `python3 -m http.server 8765`, then open `http://localhost:8765/examples/<page>.html`. Or send the bundled file. |
| A product docs site | Copy `kit/` into the site's assets and link the files. Keep one copy of the kit per site. |

## Words

- Visuals first. Add words only where they help.
- One fact per sentence. Use Simplified Technical English (ASD-STE100) as `references/ste.md` sets out: word limits, approved verb forms and approved words. Australian spelling. Each main item still needs about 4 to 8 substantive facts.
- No acronyms. Write the full words in page text, titles, labels, and pop-ups. Where knowing the short form helps, write it once in brackets after the full term, for example "Web Content Accessibility Guidelines (WCAG)". Then keep using the full term.
- No preamble, no "This diagram shows…", no slogans.
- No project chatter, internal ids or customer data on a page. Each page stands alone.

## Inline widgets

A small idea (one idea, five to nine parts) can be an inline widget instead of a page, where the harness has one. A substantial OpenClaw explainer still gets the compact inline companion; an informational companion can simply be a native **Open full explainer** link. Do not create an extra dashboard, tab or pinned widget for each decision/status item. Use neutral boxes, one red element, a transparent ground and the frame's own theme classes. A widget cannot open pop-ups, so make a page when the parts need definitions.

## Keep in step

- `references/pattern.md` copies `project/explainers.md` from the Arc Forge Design System. `kit/explainer.css` and `kit/explainer.js` copy its `project/explainer/` files. When a new rule is added, change both places. The design-system source lives in its own repository. Copy the same wording there when you can edit it.
- `references/charts.md` copies the Chart Lab ratings. When a rating changes, change the table.
- `references/chart-lab.html` copies the Chart Lab artifact page. When the artifact changes, copy it again and remove the rating form, its storage script and the Next round section.
- The diagram colour key belongs to `arcforgelabs/themes` (`docs/diagram-colour-key.md`). Copy its values; do not change them here.
- `kit/themes.js` is generated. After a change to `kit/tokens.css`, a theme in `arcforgelabs/themes` or Flow's `server/theme/themes.js`, run `scripts/sync-themes` and `scripts/validate`.
- The public copy is `arcforgelabs/themes` `explainer/`. After a change here merges, run `scripts/export-public <themes>/explainer` and open a pull request there. Never edit the public copy by hand.
- A new renderer in `kit/charts.js` must pass `scripts/check` in `examples/explainer-kit.html`. Add a section for it there.
- Threads load this skill from the `explainer` plugin in arcforgelabs/marketplace, not from this folder. A merge here reaches them only after a `Plugin Marketplace Release` run publishes it. The plugin's `PROVENANCE.json` names the tools commit it came from. After a kit fix merges, check that commit before you say the fix is live.
